Seguridad de Cita en Línea: qué revisar y cómo corregirlo

Misma revisión que se hizo para SIDECO, aplicada a siat-atencion-citas (backend + frontend, el sistema desplegado en /citaOnline/). El resultado es distinto porque el sistema es distinto: aquí no hay escalación de privilegios que revisar — y este documento explica por qué, y cuál es el riesgo real de una app pública de este tipo.

Análisis 1 de septiembre de 2026 · código real de WebSecurityConfig.java, CitaOnlineController.java, RateLimitFilter.java, RenapoServiceImpl.java, web.xml (snapshot del 28-ago)
La escalación de privilegios del retest de SIDECO no aplica aquí. Cita en Línea es una app pública de autoservicio ciudadano: una sola página (CitaOnline.xhtml), un solo controlador (CitaOnlineController, @Scope("session")), sin login, sin módulo de administración, sin roles. WebSecurityConfig es literalmente .antMatchers("/**").permitAll(). No hay un «módulo admin» detrás de un guard que se pueda alcanzar reescribiendo un 403, porque ese módulo no existe. El backend (siat-atencion-citas-backend) es una librería JPA/JSF sin capa HTTP ni @RestController.

Lo que sí hay que revisar en una app pública así

El riesgo no es «un rol bajo llega a funciones de un rol alto». Es: todo el backend está expuesto sin autenticar, así que lo que importa es (1) abuso a escala, (2) exposición de datos personales, (3) la integración con RENAPO, y (4) que las defensas que ya escribieron (filtros, CSRF) funcionen de verdad. Cinco hallazgos concretos, con su corrección.

01RateLimitFilter no limita por cliente y tiene fuga de memoriaMedia

Qué encontramos. RateLimitFilter.java:31 usa request.getRemoteAddr() como clave. La app está detrás del proxy de 10.4.2.185, así que getRemoteAddr() devuelve la IP del proxy para todo el tráfico → todos los ciudadanos comparten un solo contador de 60/min. En la práctica: o bloquea a todos cuando el tráfico agregado pasa de 60/min, o no bloquea a nadie. Además el ConcurrentHashMap (línea 16) nunca purga IPs viejas → crece sin límite.

En qué afecta. No hay control real de abuso: agendamiento masivo, flood del envío de correos, y —sobre todo— martilleo de la validación de CURP contra RENAPO (ver hallazgo 03). Y la fuga de memoria es un DoS a mediano plazo.

Cómo se corrige (sin librerías nuevas, aunque una librería lo hace mejor):

// 1. leer la IP real del cliente (el proxy debe fijar X-Forwarded-For y descartar el que envíe el cliente)
String fwd = request.getHeader("X-Forwarded-For");
String ip = (fwd != null && !fwd.isBlank()) ? fwd.split(",")[0].trim() : request.getRemoteAddr();

// 2. purgar entradas viejas: un barrido periódico, o migrar a un cache con expiración
//    (Guava Cache expireAfterWrite(1, MINUTES), o Bucket4j para rate-limiting de verdad)

Config del proxy: en nginx/Apache, proxy_set_header X-Forwarded-For $remote_addr; (no $proxy_add_x_forwarded_for, que concatena lo que mande el cliente y es falsificable).

02La protección CSRF es cosméticaMedia

Qué encontramos. WebSecurityConfig hace http.csrf().disable(). Aparte, un CsrfRenderKit/CsrfResponseWriter inyecta el CsrfToken de Spring como campo oculto en cada <form> (CsrfResponseWriter.java:49-55). Pero como Spring CSRF está deshabilitado, nadie valida ese token al recibir el POST. El campo se escribe y se ignora.

En qué afecta. Un sitio de terceros puede auto-enviar el formulario de registraCita() (bookings masivos / spam). La única barrera real hoy es el ViewState de JSF — que sí ayuda si el guardado de estado es en servidor y la vista es stateful, pero eso hay que confirmarlo, no asumirlo.

Cómo se corrige. Decidir una de dos y aplicarla de forma consistente:

// Opción A — reactivar CSRF de Spring y dejar que el token que ya se inyecta SÍ se valide
http.csrf().disable()
http.csrf(csrf -> csrf.csrfTokenRepository(CookieCsrfTokenRepository.withHttpOnlyFalse()))

// Opción B — quedarse sin Spring CSRF pero confirmar la defensa de JSF:
//   web.xml -> javax.faces.STATE_SAVING_METHOD = server  (ya está seteado, verificar el valor)
//   y que la vista NO sea <f:view transient="true"> (stateless)
//   -> en ese caso, ELIMINAR el CsrfRenderKit para no dar falsa sensación de protección

Aparte: CsrfResponseWriter.java:51 tiene comentado un System.out.println que imprimía el valor del token, y el de la línea 58 imprime a stdout en cada render. Quitar ambos.

03La validación de CURP contra RENAPO queda como oráculo abiertoMedia

Qué encontramos. registraCita() valida la CURP que teclea el ciudadano contra el registro nacional (RenapoServiceImpl). Como todo es permitAll y el rate limit no funciona (hallazgo 01), ese paso se puede invocar en bucle. Además RenapoServiceImpl importa TrustStrategy / SSLContexts / SSLConnectionSocketFactory — patrón de confianza TLS total (acepta cualquier certificado) para llamar a RENAPO.

En qué afecta. (1) Privacidad: un atacante valida/enumera CURPs a escala; una CURP codifica fecha de nacimiento, sexo y entidad — un oráculo de «existe / no existe» es un problema de datos personales. (2) Operativo: se agota la cuota del contrato con RENAPO o RENAPO bloquea la IP del servidor. (3) MITM: con confianza TLS total, un atacante en la red intercepta la consulta a RENAPO (datos personales en tránsito).

Cómo se corrige.

// a) rate limit que funcione (hallazgo 01) + una prueba humana en el paso de CURP
//    (CAPTCHA / hCaptcha / turnstile) antes de llamar a RENAPO
// b) quitar la confianza TLS total en RenapoServiceImpl:
SSLContexts.custom().loadTrustMaterial(null, (chain, authType) -> true)   // acepta cualquier cert
// usar el trust store por defecto de la JVM; si RENAPO usa una CA interna,
// importar ESA CA al truststore, no confiar en todas
// c) monitorear el volumen de llamadas a RENAPO y alertar sobre picos
04Reimpresión del comprobante — sin IDOR directo, verificar que no haya otra víaBaja

Qué encontramos. generarComprobante() (CitaOnlineController.java:868) arma el PDF (nombre, CURP, cita) a partir de citaDisponibleBean.getCitaId() que vive en el bean de sesión del ciudadano que acaba de agendar. No es un endpoint de búsqueda por folio — lee estado de sesión, así que no hay IDOR aquí. Bien.

Qué falta confirmar. Que no exista otra ruta de «reimprimir comprobante» (un enlace en el correo de confirmación, un parámetro de URL, un flujo «consulta tu cita con folio + CURP»). Si el folio (citaDisponibleBean.getCitaId()) es secuencial y en algún punto viaja en una URL o en el correo, se vuelve enumerable → datos de otros ciudadanos.

Cómo se corrige (si aparece esa vía): exigir folio + al menos otro dato personal (CURP completa o fecha de la cita) para reimprimir, y que el identificador no sea secuencial (UUID).

05Endurecimiento del build de producciónBaja

Qué encontramos. web.xml define javax.faces.PROJECT_STAGE (línea 10); hay que verificar que el artefacto de producción lo tenga en Production, no Development (que muestra árbol de componentes y trazas en las páginas de error). El commit 558cde9 «se agrega archivo de configuracion dev» — confirmar que ese perfil dev no viaja al empaquetado de producción.

En qué afecta. En Development, cualquier error de JSF expone estructura interna, rutas y a veces datos del formulario en la respuesta.

Cómo se corrige.

<context-param>
  <param-name>javax.faces.PROJECT_STAGE</param-name>
  <param-value>Production</param-value>
</context-param>
// y que el pipeline de build de prod use el profile/config correcto, no el "dev"

Checklist

  1. Arreglar RateLimitFilter: X-Forwarded-For + purga/expiración del mapa; configurar el proxy para fijar la cabecera de forma no falsificable.
  2. Decidir CSRF: reactivar Spring CSRF o confirmar el STATE_SAVING de JSF y quitar el CsrfRenderKit engañoso. Quitar los System.out.println de CsrfResponseWriter.
  3. Poner CAPTCHA en el paso de CURP y quitar la confianza TLS total de RenapoServiceImpl; monitorear volumen de llamadas a RENAPO.
  4. Confirmar que no hay una vía de reimpresión de comprobante por folio enumerable.
  5. PROJECT_STAGE=Production en el build de producción; verificar que el config «dev» no se empaqueta.
  6. Repasar la tabla «lo que ya está bien» y confirmar cada control con una prueba.
