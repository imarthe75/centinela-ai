Escalación de privilegios en SIDECO: solución por módulo y por método

Guía de remediación para la observación del retest (cuenta TcsCSA2, sin rol de administrador, alcanzó el módulo de administración de usuarios y modificó usuarios y roles). Cubre el codebase backend-sideco-develop (ResourceServer + frontend Angular). Cada corrección trae el código exacto y cómo verificarla.

Análisis 1 de septiembre de 2026 · basado en el código real de ResourceServerConfig.java, UsuarioController.java, CatalogoController.java y autorizacion.guard.ts
Resumen. El endpoint que el atacante usó (GET /v1/usr/getUsuarios) no tiene ninguna regla de autorización: cae en .antMatchers("/v1/**").authenticated(), así que basta una sesión válida. Pero no es un solo hueco: hay cinco defectos que se combinan. Aunque se tape el /v1/usr/**, la función RoleSecurity.isAdmin() se puede burlar con un nombre de usuario que contenga la cadena «admin», y siatSecurity.test() se usa como alternativa a estar autenticado (spoofeando la cabecera Referer). Este documento los corrige todos.

01Cómo lo hizo el atacante

La cadena, paso a paso, para entender qué corrige cada cambio:

  1. Se autentica con una cuenta real de bajo privilegio (TcsCSA2, rol no administrador).
  2. El frontend pide catalogosAdmin; el AutorizacionGuard de Angular llama al backend (POST /v1/usr/revisarRolRuta) para saber si ese rol ve la ruta. La respuesta es «no» → el guard redirige a /.
  3. Con una herramienta de interceptación, reescribe esa respuesta de 403 a 200 OK. El guard cree que sí y renderiza el módulo administrativo (la clase CatusuariosadminComponent ya venía descargada en el bundle).
  4. El componente ya montado hace su llamada de datos: GET /v1/usr/getUsuarios. El backend no exige rol admin en /v1/usr/** → responde 200 con la lista completa de usuarios.
  5. Desde ahí, POST /v1/usr/guardarUsuarios y PUT /v1/usr/accesoSistema/{id} —también sin rol— le permiten editar usuarios y asignar roles elevados.

El punto 3 es la barrera solo-cliente. El punto 4 es la barrera que falta en el servidor. Hay que cerrar el 4 (obligatorio) y reforzar el 3.

02Los cinco defectos

ASin regla para /v1/usr/**

UsuarioController está en @RequestMapping("/v1/usr/"). En ResourceServerConfig.java se blindan por nombre /v1/catalogos/roles*, /v1/catalogos/catMenu*, obtenerAllRoles, etc. con @roleSecurity.isAdmin, y las mutaciones de /v1/catalogos/** con POST/PUT/DELETE. Pero nada cubre /v1/usr/**: cae en la regla final .antMatchers("/v1/**").authenticated() (línea 78). Todos los métodos de administración de identidad quedan a nivel «cualquier usuario con token».

BRoleSecurity.isAdmin() se burla con el nombre de usuario

La función decide «es admin» con cuatro contains("admin") sobre cadenas: auth.getName(), cada GrantedAuthority, el claim authorities y el claim user_name. Un usuario llamado radminez, adminis_prueba, gadmine —o cualquier cadena que contenga «admin»— pasa como administrador. Aunque se corrija el defecto A, este deja abierta la escalada por el solo hecho de nombrar la cuenta.

CsiatSecurity.test() usado como alternativa a autenticarse

Las reglas de /v1/catalogos/** y /v1/calc/** son .access("isAuthenticated() or @siatSecurity.test(request)"). siatSecurity.test() sólo mira las cabeceras Origin / Referer contra una lista de dominios *.edomex.gob.mx. Cualquier cliente que no sea un navegador (curl, Postman, la herramienta del pentester) fija esa cabecera a mano y pasa el or sin token. Es una señal anti-CSRF, no autorización.

DEl módulo admin del frontend se protege sólo en el navegador

catalogos-admin-routing.module.ts:12 usa canActivate:[AutorizacionGuard]. El guard llama a revisarRoles(url) y navega a / si es false — una decisión del lado del cliente sobre una respuesta HTTP interceptable. Además, en layoutcompleto-routing.module.ts:158 la ruta padre catalogosAdmin (loadChildren) no tiene canActivate; sólo lo tiene la ruta hija, y el componente ya viaja en el bundle.

EhttpBasic() + csrf().disable()

ResourceServerConfig habilita http.httpBasic() junto al resource server JWT y deshabilita CSRF. Basic Auth reenvía usuario y contraseña en cada petición y amplía la superficie; con CSRF apagado, cualquier hueco de autorización es explotable también desde una página de terceros si la sesión usa cookie. Si el acceso real es 100% Bearer JWT, httpBasic() sobra.

ResourceServer/…/config/ResourceServerConfig.java · RoleSecurity.isAdmin()Defecto B

Reemplazar los cuatro contains("admin") por comparación exacta contra una lista de authorities/roles válidos. El contains sobre getName() / user_name se elimina por completo — el nombre de usuario nunca debe otorgar privilegios.

public static class RoleSecurity {

    // Roles/authorities que SÍ son administrador. Ajustar a los valores reales
    // que emite el AuthServer en el claim "authorities".
    private static final java.util.Set<String> ROLES_ADMIN = java.util.Set.of(
            "ADMINISTRADOR", "ROLE_ADMINISTRADOR", "ADMIN_SIDECO", "SUPER_ADMIN");

    public boolean isAdmin(org.springframework.security.core.Authentication auth) {
        if (auth == null || !auth.isAuthenticated()) return false;

        // 1. GrantedAuthorities: comparación EXACTA (no substring)
        boolean granted = auth.getAuthorities().stream()
            .map(a -> a.getAuthority() == null ? "" : a.getAuthority().trim().toUpperCase())
            .anyMatch(ROLES_ADMIN::contains);
        if (granted) return true;

        // 2. Claim "authorities" del JWT: comparación EXACTA elemento por elemento
        if (auth.getPrincipal() instanceof org.springframework.security.oauth2.jwt.Jwt jwt) {
            Object claim = jwt.getClaims().get("authorities");
            if (claim instanceof java.util.Collection<?> col) {
                for (Object r : col) {
                    if (r != null && ROLES_ADMIN.contains(r.toString().trim().toUpperCase())) return true;
                }
            } else if (claim != null) {
                if (ROLES_ADMIN.contains(claim.toString().trim().toUpperCase())) return true;
            }
        }

        // ELIMINADO: auth.getName().contains("admin")
        // ELIMINADO: claim "user_name".contains("admin")
        // ELIMINADO: authority.contains("admin")   (substring)
        return false;
    }
}

Antes de desplegar B: confirmar con el equipo del AuthServer qué string exacto lleva el claim authorities para un administrador (¿"Administrador", "ROLE_ADMIN", un id numérico?). Poblar ROLES_ADMIN con ese valor real y probar con una cuenta admin legítima antes de subir, o los administradores reales pierden acceso.

4.1 — Los tres casos que no son «todo o nada»

IDOR — /usuariobyId/{id}, /obtenerCorreoPorId/{id}, /getUsuarios/{idUnidad}

Si el negocio necesita que un usuario consulte su propio registro (o los de su unidad) sin ser admin, la regla no puede ser sólo isAdmin. Añadir la comprobación de pertenencia en el servicio:

public UsuarioConsultaDTO usuarioPorId(Long idPedido, Authentication auth) {
    Long idToken = usuarioService.idDe(auth.getName());        // id del usuario autenticado
    boolean admin = new RoleSecurity().isAdmin(auth);
    if (!admin && !idToken.equals(idPedido)) {
        throw new AccessDeniedException("No autorizado para consultar este usuario");
    }
    return usuarioService.getById(idPedido);
}

Para /getUsuarios/{idUnidad}: comparar idUnidad contra la unidad del token; si no coincide y no es admin → 403.
