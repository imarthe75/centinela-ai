Integración Authentik–Centinela ITDR

Conecta los eventos de autenticación de Authentik al motor de Detección y Respuesta ante Amenazas de Identidad (ITDR) de Centinela, para que un ataque de fuerza bruta o password spraying aparezca en el tablero en tiempo real.

Sistema a configurar Authentik (10.4.3.208) Destino Centinela ITDR (10.4.3.34) Tiempo ~15 min Perfil Administrador de Authentik

En resumen

  1. Definir un token compartido en Centinelaopcional pero recomendado
  2. Crear la asignación de cuerpo del webhook
  3. Crear la asignación de encabezado del webhooksi hiciste el paso 1 del token
  4. Crear el Medio de Notificación (transporte webhook)
  5. Crear la política que selecciona qué eventos disparan
  6. Crear la Regla de Notificación y vincular la política
  7. Crear un token de API para la respuesta autónomaopcional
  8. Verificar de extremo a extremo

Antes de empezar

  • El servidor de Authentik (10.4.3.208) debe tener ruta de red hacia Centinela (10.4.3.34) en el puerto 443.
  • Necesitas acceso de administrador a la interfaz de Authentik.
  • Para el paso 1 y el paso 6 necesitas una sesión de terminal en el host de Centinela con permiso para editar /opt/centinela-ai/.env y correr docker compose.
  • URL del webhook de Centinela: https://centinela.casmart.internal/api/itdr/authentik/webhook
1

Definir un token compartido en Centinela

Evita que cualquiera con acceso a la red pueda inyectar alertas de identidad falsas en el tablero.

En el host de Centinela (10.4.3.34):

openssl rand -hex 24                     # genera un token
echo 'ITDR_WEBHOOK_TOKEN=<el-token>' >> /opt/centinela-ai/.env
cd /opt/centinela-ai && docker compose up -d centinela-backend

Guarda el token: lo usas en el paso 3. Si omites este paso, el webhook queda abierto y Centinela lo registra con una advertencia en su bitácora.

2

Crear la asignación de cuerpo del webhook

Hace que Centinela reciba la IP de origen y la acción reales, no solo el texto de la notificación.

En Authentik: Personalización → Property Mappings → Crear → Notification Webhook Mapping (Asignación de webhook de notificaciones).

NombreCentinela ITDR - cuerpo
ExpresiónLa de abajo

Expresión

event = notification.event
ctx = (event.context or {}) if event else {}
return {
    "action": str(event.action) if event else "login_failed",
    "username": ((event.user or {}).get("username") if event else "") or ctx.get("username", ""),
    "client_ip": event.client_ip if event and event.client_ip else "0.0.0.0",
    "context": ctx,
}
Por qué

En un inicio de sesión fallido, el nombre de usuario tecleado suele venir en event.context["username"] aunque la cuenta no exista. La expresión lo toma de ahí como respaldo, y Centinela hace lo mismo.

3

Crear la asignación de encabezado del webhook

Envía el token compartido en cada llamada. Sáltate este paso si omitiste el paso 1.

Personalización → Property Mappings → Crear → Notification Webhook Mapping.

NombreCentinela ITDR - encabezado

Expresión

return {"X-Centinela-Token": "<pega-aqui-el-token-del-paso-1>"}
4

El transporte tipo webhook que llama a Centinela.

Eventos → Medios de Notificación → Crear.

5

Crear la política que selecciona qué eventos disparan

Sin esto, la regla se dispararía con cualquier evento. Queremos solo los inicios de sesión fallidos.

Personalización → Políticas → Crear → Event Matcher Policy (Política de coincidencia de eventos).

NombreCentinela ITDR - Login Fallido
Acciónlogin_failed
Deja el resto de campos vacíos.
Ampliar más adelante

Para cubrir también borrado de dispositivos MFA y cambios de privilegios, crea políticas adicionales con Acción model_deleted y user_write, y vincúlalas en el paso 6. Centinela ya tiene las reglas de detección para esos casos.

6

Crear la Regla de Notificación y vincular la política

Une "qué eventos" (política) con "a dónde se manda" (transporte).

Eventos → Reglas de notificación → Crear.

CampoValor
NombreCentinela ITDR
GrupoUn grupo que tenga al menos un miembro (por ejemplo authentik Admins).
TransportesCentinela ITDR del paso 4
Severidadalert
Obligatorio

Si el grupo está vacío, Authentik no genera la notificación y el webhook nunca se llama. Usa un grupo con miembros reales.

Luego abre la regla recién creada → pestaña de vinculaciones de políticas (Policy Bindings) → Vincular política existente → Centinela ITDR - Login Fallido.

7

Crear un token de API para la respuesta autónoma

Opcional. Permite que Centinela desactive automáticamente al usuario bajo ataque de fuerza bruta.

  • Directorio → Usuarios → Crear cuenta de servicio (Service account), o Directorio → Tokens → Crear → genera un API token.
  • Otórgale permiso sobre authentik_core.view_user y authentik_core.change_user (o un rol de administrador acotado).
  • En el host de Centinela:
echo 'AUTHENTIK_API_TOKEN=<el-api-token>' >> /opt/centinela-ai/.env
cd /opt/centinela-ai && docker compose up -d centinela-ai centinela-backend
No reutilizar

El AUTHENTIK_CLIENT_SECRET ya configurado no sirve para esto: es un secreto de OAuth, no un token de API. Centinela lo probó en vivo y Authentik responde 403 Token invalid/expired.

8

Verificar de extremo a extremo

Confirma que el evento llega, dispara la regla y aparece en el tablero.

Desde cualquier equipo con red hacia Centinela:

for i in $(seq 1 6); do
  curl -sk -X POST https://centinela.casmart.internal/api/itdr/authentik/webhook \
    -H 'Content-Type: application/json' \
    -H 'X-Centinela-Token: <token del paso 1, si aplica>' \
    -d '{"action":"login_failed","username":"prueba_itdr","client_ip":"198.51.100.7"}'
done
  • La 5.ª o 6.ª respuesta debe incluir "rule_name":"ITDR-AUTHENTIK-BRUTE-FORCE".
  • En el tablero, Identidad & ITDR muestra el evento (ventana de 15 min) y Búsqueda de Amenazas también.
  • Prueba real: falla 5 inicios de sesión seguidos en Authentik con cualquier usuario, dentro de 1 minuto.

Limpieza después de probar

docker exec centinela-backend python3 -c "import sys;sys.path.insert(0,'/app');from core import db_manager
with db_manager.get_db_cursor() as c:
 c.execute(\"DELETE FROM runtime_alerts WHERE alert_text LIKE '%prueba_itdr%' OR alert_text LIKE '%198.51.100.7%'\")
 print('ok')"

docker exec centinela-clickhouse clickhouse-client -q \
  "ALTER TABLE centinela_telemetry.telemetry_events DELETE WHERE username='prueba_itdr' OR client_ip='198.51.100.7'"

Qué detecta Centinela con estos eventos

ReglaSe dispara cuandoAcción autónoma
ITDR-AUTHENTIK-BRUTE-FORCE ≥ 5 login_failed del mismo usuario + IP en 60 segundos Intenta desactivar la sesión del usuario requiere el paso 7
ITDR-AUTHENTIK-MFA-BYPASS Evento de MFA con remove o delete Solo alerta
ITDR-AUTHENTIK-PRIVILEGE-ESCALATION Evento de grupo con add o admin Intenta desactivar la sesión del usuario

Cada evento se escribe en dos lugares: ClickHouse (lo que consume la pantalla Identidad & ITDR, ventana de 15 min) y PostgreSQL runtime_alerts (lo que consume Búsqueda de Amenazas, sin límite de tiempo).

Si algo no aparece

SíntomaCausa probable
El curl de prueba responde pero no pasa nada en el tableroMenos de 5 intentos en la ventana de 60 s, o distinto usuario/IP en cada intento.
El curl responde 401El encabezado X-Centinela-Token no coincide con ITDR_WEBHOOK_TOKEN del .env.
Fallas reales en Authentik no llegan, pero el curl síEl grupo de la Regla de Notificación está vacío, o la política no quedó vinculada a la regla.
Llega el evento pero client_ip es 0.0.0.0La asignación de cuerpo (paso 2) no está seleccionada en el transporte, o el evento no traía IP.
Aparece en Búsqueda de Amenazas pero no en Identidad & ITDREl evento tiene más de 15 minutos; esa pantalla solo muestra la ventana reciente.
