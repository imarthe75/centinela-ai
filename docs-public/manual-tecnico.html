Centinela-AI

Plataforma SOC/SOAR para la infraestructura CASMARTS: escaneo continuo de vulnerabilidades, correlación con IA, y remediación automatizada con supervisión humana.

Versión del motor Aura-Guard v2026.4.2 Stack Docker Compose, PostgreSQL, Wazuh, GitLab

Qué es Centinela-AI

Centinela-AI es la plataforma central de seguridad de CASMARTS. Descubre activos automáticamente (servidores, bases de datos, repositorios de GitLab, contenedores), los audita con más de una decena de motores de escaneo especializados, usa un modelo de lenguaje para correlacionar cada hallazgo en un reporte ejecutivo con una remediación concreta, y — cuando un humano aprueba esa remediación — la ejecuta de forma automatizada: por Ansible sobre un servidor real, o abriendo un Merge Request sobre un repositorio de código.

No es un solo escáner: es la capa de orquestación que conecta descubrimiento, escaneo, análisis y respuesta en un solo flujo, con un tablero (dashboard) como punto único de visibilidad.

Ciclo de vida de un hallazgo

  1. 1

    Descubrimiento

    El orquestador registra activos automáticamente: agentes Wazuh que se conectan, bases de datos configuradas, y todos los proyectos de la organización de GitLab vía su API. Cada activo recibe un tipo (SERVER, AppServer, Database (SQL), GitLab-Repo) que determina qué motores le aplican.

  2. 2

    Escaneo

    Cada activo se audita con los motores correspondientes a su tipo — infraestructura real recibe Nuclei/ZAP/Nmap; repositorios de código reciben SAST/SCA/análisis de estándares; contenedores reciben Trivy/Grype. Cada hallazgo se registra en vulnerability_log con un identificador propio.

  3. 3

    Correlación con IA

    Un LLM analiza cada hallazgo nuevo: lo clasifica, redacta un resumen ejecutivo y evalúa el impacto de negocio, y genera la remediación concreta — un script para infraestructura, o un parche de código (diff) para un repositorio.

  4. 4

    Remediación (SOAR)

    Un operador revisa y aprueba desde el dashboard. Sentinel ejecuta: sobre un servidor real, corre el script vía Ansible con las credenciales de Vault; sobre un repositorio, clona, aplica el parche, y abre un Merge Request para revisión humana — nunca hace push directo a la rama principal.

Origen

Qué significa
La respuesta HTTP no especifica Cache-Control: no-store, lo que permite que un proxy o navegador intermedio almacene en caché una respuesta potencialmente sensible.

De dónde vienen los catálogos de vulnerabilidades

La fuente cambia según el motor — unos traen su propio catálogo embebido, otros sincronizan una base de datos pública, y los tres motores propios de Centinela usan reglas escritas a mano.

Catálogos externos, sincronizados en vivo

  • Nuclei — usa nuclei-templates, el repositorio comunitario público que la herramienta actualiza por su cuenta.
  • Trivy / Grype — mantienen una base de datos local que sincronizan periódicamente contra NVD, GitHub Advisory Database, y los avisos de seguridad de las distribuciones Linux.
  • sca-native — consulta OSV.dev (Open Source Vulnerabilities, el proyecto de Google que agrega NVD, GitHub Advisories, PyPA y npm en una sola API pública) por cada paquete y versión exacta encontrados en requirements.txt/package.json, en tiempo real, en cada escaneo — no una tabla fija.
  • ZAP — trae su catálogo de alertas embebido en la propia herramienta (el índice público en zaproxy.org es la documentación de ese mismo catálogo, no una fuente externa que se consulte en cada escaneo).

Reglas propias de Centinela

sast-native y standards-audit no descargan nada — son patrones (expresiones regulares y análisis de sintaxis) escritos específicamente para Centinela, para detectar código peligroso y violaciones de STRIDE/ISO 25010.

Nota de alcance

sca-native conserva una tabla estática pequeña (7 paquetes) exclusivamente como respaldo si OSV.dev no responde — un corte de red no debería significar cero cobertura de dependencias. En operación normal, OSV.dev es la fuente real y se consulta en cada escaneo.

Motor de Inteligencia Artificial

Cada hallazgo nuevo pasa por correlate_vulnerability(), que arma un prompt con el tipo de activo, la severidad, la ubicación exacta y la evidencia técnica, y lo envía a un modelo de lenguaje.

Cadena de proveedores

Groq, Google Gemini, NVIDIA NIM y OpenRouter se inicializan de forma independiente al arrancar (cada uno si tiene una API key configurada), y cada llamada de correlación — no solo el arranque del proceso — recorre la cadena en orden hasta obtener una respuesta real:

groq → google_genai → nvidia_nim → openrouter → motor heurístico

Antes, se elegía un único proveedor al arrancar el contenedor y se usaba durante toda su vida — si ese proveedor agotaba su cuota a mitad del día, todo hallazgo posterior caía directo al motor heurístico aunque otros proveedores tuvieran API key configurada y cupo disponible. Ahora cada llamada intenta los cuatro. El orden se eligió por latencia real medida contra el prompt de correlación: Groq y Gemini responden en segundos (Gemini además con modo JSON real vía response_mime_type); NVIDIA y OpenRouter son más lentos e impredecibles (NVIDIA con respuestas de hasta 65s, OpenRouter con límites de tasa compartidos entre todos los usuarios de sus modelos gratuitos), así que se dejaron al final con timeout/max_retries acotados para que un proveedor colgado no bloquee toda la correlación.

Hallazgos sintéticos: sin LLM por diseño

Los hallazgos que son marcadores propios del sistema — HOST-CONTAINMENT-REQUEST, CTI-IOC-MATCH-*, BLOODHOUND-PATH-*, SCAN-AUDIT, HEURISTIC-SECURITY-DEBT, CIS-BENCHMARK-AUDIT — nunca se envían al LLM: van directo al motor heurístico, que ya tiene la respuesta correcta y específica para cada uno. Se detectó en vivo que pedirle a un LLM genérico que "corrija" un hallazgo sintético como HOST-CONTAINMENT-REQUEST lo hacía alucinar un script de infraestructura no relacionado (marcado como automatizable) en vez de generar el bloqueo de firewall real — un riesgo real si un operador lo hubiera aprobado sin leerlo con cuidado.

Motor de respaldo (sin IA disponible)

Si ningún proveedor responde (cuota agotada, sin conexión), Centinela no deja el hallazgo sin analizar: un motor heurístico determinístico genera texto y — cuando es un caso conocido y seguro — un script real específico por categoría (hardening SSH, cabeceras nginx para ZAP, USER no-root en Dockerfile, etc.). Cuando no hay una regla determinística para ese caso, lo indica honestamente en vez de simular una corrección.

Validación de respuestas de IA de baja calidad

Un LLM que sí responde no garantiza una respuesta útil: se detectaron casos reales donde el modelo devolvía texto de relleno en remediation_script (p. ej. "... (script proporcionado)") en vez de un script real, y ese texto se guardaba tal cual — en algunos casos incluso marcado como automatizable. Centinela ahora valida el contenido antes de aceptarlo: si es solo una elipsis con una nota de relleno, o es demasiado corto para ser un script real, se descarta y se usa el motor heurístico determinístico en su lugar, igual que si la IA nunca hubiera respondido.

SOAR y remediación automatizada

Sentinel monitorea remediaciones aprobadas (approval_token = 'APPROVED') y las ejecuta según el tipo de activo:

Infraestructura real (SERVER, AppServer)

Ejecuta el script vía Ansible contra la IP del activo, autenticando con la llave SSH o contraseña sudo almacenada en Vault (casmarts/ansible/{activo}). Si la ejecución falla, el hallazgo queda marcado FAILED — nunca se fuerza a COMPLETED sin una corrección real.

Repositorios de GitLab

Clona el repositorio, aplica el parche (determinístico para Dockerfile/dependencias, o el diff generado por IA), y hace commit + push a una rama nueva (centinela-fix/*). Abre un Merge Request para revisión humana — nunca hace push directo a la rama principal.

Aprobación humana en el centro

Ningún cambio se aplica sin que un operador apruebe desde el dashboard. La IA propone; Sentinel ejecuta solo lo aprobado; y toda ejecución queda registrada con su resultado real.

Wazuh EDR y Zeek NDR

Wazuh Manager (EDR)

Wazuh Manager corre como servicio propio del stack, con tres puertos publicados en este despliegue:

PuertoFunción

1515Inscripción de agentes nuevos (enrollment)

Wazuh define otros puertos en su arquitectura general (514 syslog, 9200 indexer, 5601 dashboard) que no están desplegados en este entorno — este stack corre solo el Manager, sin Indexer ni Dashboard propios de Wazuh.

Zeek (NDR)

Zeek observa el tráfico de red en vivo y escribe dos tipos de log distintos: notice.log (solo eventos que la política interna de Zeek considera dignos de nota — vacío en este despliegue, porque el tráfico normal no dispara ninguna) y conn.log (registro continuo de cada conexión, siempre activo). Centinela procesa conn.log en tiempo real: cruza la IP de origen y destino de cada conexión contra el feed de inteligencia de amenazas (ver Omni-XDR), y — para que la salud del sistema refleje actividad real y no solo "algo malo en las últimas 24h" — emite un latido honesto cada 5 minutos con el número real de conexiones observadas.

Cumplimiento normativo

Un módulo separado (compliance_mapper.py) no detecta nada por sí mismo — toma los hallazgos que ya existen y los mapea contra los controles de los marcos regulatorios más comunes:

ISO 27001:2022 NIST SP 800-53 PCI-DSS v4.0 SOC 2 GDPR

Sirve para responder "¿qué controles regulatorios están en riesgo?" sin re-escanear nada — es una capa de reporte sobre los hallazgos ya recolectados.

Visión Omni-XDR 2.0

Centinela-AI está evolucionando hacia una plataforma Omni-XDR unificada. Estado real por capacidad — solo se documenta aquí lo verificado en vivo, no lo planeado:

CapacidadEstadoDetalle
Centinela Risk Score (CRS) ✅ Real Puntuación 0-100 combinando severidad, EPSS real (probabilidad de explotación, FIRST.org) y estado real de CISA KEV (explotación confirmada en el mundo real) más criticidad del activo. Se recalcula en segundo plano y se revalida cada 24h.
Deduplicación cross-tool ✅ Real Si dos motores distintos (ej. Nuclei y el motor SCA) detectan la misma vulnerabilidad real de forma independiente, se fusiona en un solo hallazgo en vez de duplicar el ticket.
Control de SLA por severidad ✅ Real Plazos de remediación automáticos: Crítico 24h, Alto 7 días, Medio 30 días, Bajo 90 días, con indicador de vencimiento.
Quality Gates ✅ Real Evaluación de umbrales de calidad (vulnerabilidades críticas/altas, violaciones ISO 25010) con resultado pass/fail y grado A/B/F, consultable vía API para integrarse a un pipeline CI/CD.
Análisis de alcanzabilidad de código ✅ Real Para dependencias vulnerables: verifica si el paquete realmente se importa en el código (vs. solo declarado en el manifiesto y nunca usado), etiquetando cada hallazgo como REACHABLE o UNREACHABLE para reducir falsos positivos.
Parcheo virtual ✅ Real Cuando una IP confirmada como servidor de comando-y-control activo (fuente pública en vivo) coincide con uno de nuestros activos, se bloquea a nivel de reverse-proxy sin tocar el código de la aplicación ni reiniciar el servicio.
Matriz MITRE ATT&CK® ✅ Real Los hallazgos con una técnica de ataque real y verificable se mapean a su ID oficial de ATT&CK. Los hallazgos de calidad de código (no son técnicas de ataque) se dejan intencionalmente sin mapear en vez de forzar una clasificación falsa.
Auditoría de hardening CIS ✅ Real Subconjunto de ~11 verificaciones reales (SSH, permisos de archivos críticos, firewall, cuentas sin contraseña, auditoría, sincronización de tiempo) ejecutadas en vivo por SSH sobre el activo, con grado A-F. No es el benchmark oficial completo de CIS.
Feeds de inteligencia de amenazas (CTI/IoC) ✅ Real Cruce en vivo contra una fuente pública de IPs de servidores de comando-y-control activos, tanto contra los activos registrados como contra alertas de red en tiempo real.
Aislamiento de host (contención de emergencia) ✅ Real Solicitud de aislamiento de red de un activo comprometido, disponible desde el dashboard. Como cualquier otra remediación, requiere aprobación humana explícita antes de ejecutarse — nunca se dispara automáticamente.
Grafo de rutas de ataque (Active Directory) 🕒 Latente (por diseño) La consulta de rutas de escalamiento hacia Domain Admins es real y ahora coincide con cualquier dominio (antes estaba fijada al nombre de dominio ficticio INTERNAL.LOCAL, un error real que habría hecho que nunca encontrara nada incluso con datos reales cargados — corregido y verificado contra un grafo Neo4j sintético desechable). El grafo no tiene datos reales de Active Directory todavía — requiere ejecutar una herramienta de recolección (SharpHound/AzureHound) contra el dominio real, con credenciales de dominio que no están disponibles en este momento. Se mantiene activo en segundo plano (una consulta cada 10 minutos contra un grafo vacío, sin costo real) en vez de desactivarse, para que el día que exista un dominio AD real no haga falta re-verificar nada: solo importar los datos.

Otros componentes

  • HashiCorp Vault — único lugar donde viven las credenciales de Ansible (llaves SSH, contraseñas sudo) por activo. Nunca se guardan en la base de datos ni en el código.
  • Neo4j / BloodHound — modela el dominio de Active Directory como grafo para encontrar rutas de escalamiento hacia cuentas privilegiadas (ver detalle en Wazuh/Zeek y en Omni-XDR).

Salud del ecosistema y reportes

El dashboard tiene una vista de "Salud del Ecosistema" (GET /api/health) que reporta el estado real de cada motor y servicio — no valores fijos. Para los bucles que corren en segundo plano (feed CTI, revalidación de EPSS/KEV, latido de Zeek, CIS Benchmarks), el estado se infiere de evidencia real reciente en la base de datos, no de si el módulo simplemente se pudo importar. CIS Benchmarks corre solo cada 7 días por activo (además de poder dispararse bajo demanda), así que en un despliegue nuevo, antes de su primer ciclo, se reporta honestamente como "Disponible (bajo demanda, aún sin ejecutar)" en vez de un falso "Online". Contención de emergencia, al ser una acción deliberadamente manual (nunca automática, por diseño), se mantiene siempre como "Disponible (bajo demanda)" — ese estado se muestra en color ámbar en el dashboard, no en rojo como una falla real ni en verde como si ya hubiera corrido.

Dos reportes PDF están disponibles desde el dashboard:

  • Reporte Ejecutivo (/api/reports/executive) — nivel de riesgo global calculado a partir del Centinela Risk Score real (no solo un conteo de severidades), conteo de hallazgos con CISA KEV confirmado, incumplimientos de SLA, y las 5 técnicas MITRE ATT&CK más frecuentes.
  • Reporte de Cobertura (/api/reports/coverage) — para cada activo, qué motores corrieron y con qué resultado (aprobado, con hallazgos, o sin analizar todavía).
